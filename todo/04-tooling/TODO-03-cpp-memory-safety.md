# TODO-03 -- Memory-safety checks in the C and C++ toolchain kit

> **Goal:** A C or C++ project that installs `toolchain-cpp` declares the memory-safety hardening it builds with, and one command says whether its compile commands and its built binaries really carry it, on Windows and Linux, so a project cannot ship an unhardened or sanitizer-instrumented binary without a check naming what is missing. The kit checks and documents; it never chooses a project's flags or edits its build.

> **Current state:** Measured 2026-11-16. `kits/toolchain-cpp/` pins tools, checks the compile database, wraps a compiler cache and seeds clangd, and says nothing about memory safety: `git grep -n -i -E "fsanitize|_LIBCPP_HARDENING|_MSVC_STL_HARDENING|guard:cf|mguard|stack-protector|AddressSanitizer" -- kits global` prints nothing. The owner reviewed every C++ repository on the machine that day and found the coverage uneven: Isotone has control-flow guard, shadow stack, `/analyze`, a sanitizer lane and fuzzing; CarbonCD and Crownroot had no memory-safety option at all; none switched on standard library hardening. Measured the same day on probe programs (an out-of-bounds `std::vector` read): MSVC 19.52 exits 0 plain and `0xC0000409` with `/D_MSVC_STL_HARDENING=1`; llvm-mingw clang 23.1.1 exits 0 plain and `0xC000001D` with `-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST`; g++ 15.2.0 exits 0 plain and 134 with `-D_GLIBCXX_ASSERTIONS`. On llvm-mingw `-mguard=cf` set the Control Flow Guard image flag and `-Wl,--cetcompat` was refused by lld while `-Wl,-Xlink=-cetcompat` set the shadow-stack flag. Each project then planned its own check script (Resolute-SDK `D00 T01 §10`, CarbonCD `D00 T01 §11`, Crownroot's build tooling section 10), which is the copy-per-project this kit exists to end. Two of them, Resolute-SDK and CarbonCD, already have this kit installed. **Measured 2026-11-17** (`D04 T03 §4`, probe programs in scratch, each beside a control build without the option): with GCC 15.2.0 (Ubuntu 26.04 in WSL) and Clang 19.1.7 (Ubuntu), a `strcpy` of 69 bytes into `char buf[8]` at `-O0` ends in a segmentation fault (exit 139) with `-fno-stack-protector` and in `*** stack smashing detected ***` (exit 134) with `-fstack-protector-strong`; the same at `-O2 -fno-stack-protector` ends in exit 139 with `-D_FORTIFY_SOURCE=0` and in `*** buffer overflow detected ***` (exit 134) with `-D_FORTIFY_SOURCE=2` and `=3`; an uninitialised `int` read after a call that filled the stack prints 2067949718 (GCC) and 1515870810 (Clang) plain and 0 with `-ftrivial-auto-var-init=zero`; `hardening-check.py` reads RELRO and BIND_NOW on a GCC `-Wl,-z,relro,-z,now` PIE and BIND_NOW missing with `-z,lazy` or, on Clang, with `-z,relro` alone. Ubuntu's GCC 15.2.0 turns on `-fstack-protector-strong`, `-fstack-clash-protection`, `_FORTIFY_SOURCE=3` (with optimisation), PIE and `-z now` by itself (`gcc -Q --help=common`, `gcc -dM -E -O2`, `gcc -v`), while Ubuntu's Clang 19.1.7 left the stack protector out of a plain build. MSVC 19.52.37029 turns warning C4700 (an uninitialised local read) into error C4700 under `/sdl`. The probe sources and the exact commands, with their controls, are in `kits/toolchain-cpp/templates/docs/toolchain-cpp.md` (The probes). Not measured here: `-fstack-protector-strong` and `-ftrivial-auto-var-init=zero` on llvm-mingw (measured on Linux Clang only), and `_FORTIFY_SOURCE` with any C library but glibc.

## Outcome

- `python scripts/hardening-check.py` in a project reads the `hardening` key of `.conclave/toolchain-cpp.json` and prints one line per requirement: each definition or option on the compile commands of the project's own sources, and each image property of the binaries it names, `ok` or missing by name.
- `python forge.py doctor <project> toolchain-cpp` shows the same as `hardening` rows, and `optional` when the project declares no `hardening` key.
- The `cpp-toolchain` skill and `docs/toolchain-cpp.md` tell an agent which options each compiler family takes, how to prove one by the result it changes beside a control build (a probe that must end in the option's own trap for a runtime check, the value an initialising option sets, the image check for a link property), that a sanitizer build is a test build, and that a hardened shipped tool needs a crash message. **Corrected 2026-11-17:** this said "a probe that must trap" for every option, which the plan review of `D04 T03 §4` showed wrong for an initialising option and a link property.

## 1. Hardening Policy in the Pin File

> **Started:** 2026-11-16T18:09:39Z

**Corrected 2026-11-16:** the plan put the `hardening` loader in `hardening-check.py`, but `load_pin_file` in `scripts/toolchain-check.py` owns the pin file's format and refuses an unknown top-level key (`TOP_OPTIONAL`), so `toolchain-check.py`, `compdb-check.py` and the doctor would all refuse a pin file that declares a policy. The loader is added there, as `compdb` was, and the web kit's byte-for-byte copy follows. `binaries` moves to §2 with `image` and `test_binaries`, so no key is loaded before something reads it. The matching rules the plan left open are stated in the items: which entries are definitions and which options, that the last occurrence on a command wins, response files, and how a `command` string is split. A policy that matches no first-party entry is `unknown`, never a pass.

A project states what it builds with, and the check holds its compile commands to that. Standard library hardening leaves no mark on a binary's headers, so the compile database is the only place a read-only check can see it. The check must not guess a policy: a project with no `hardening` key gets no finding.
