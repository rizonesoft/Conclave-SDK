## adversarial: needs-attention

1. **P2: Concurrent setup runs can delete each other’s temporary files.** `kits/toolchain-cpp/templates/scripts/cc-cache.py:169` deletes every file outside its own keep set, including another invocation’s `.cc-cache-*.tmp`. Reproduce by starting two build configurations concurrently for the same project. If one reaches cleanup while the other is writing its temporary file, cleanup removes that file on POSIX, causing the other invocation’s `os.replace` to fail. On Windows, deleting the open file can instead fail cleanup. Either build can exit 1 despite valid configuration. Setup needs coordination across the complete write-and-cleanup operation.

## integration: needs-attention

2. **P1: Resolving compiler symlinks changes compiler behaviour.** `kits/toolchain-cpp/templates/scripts/cc-cache.py:84` returns `path.resolve()`, discarding the invocation name. On a normal LLVM installation where `clang++` links to `clang`, activate the wrapper with `cc-cache.py clang++`, then link a C++ program using `std::cout`. The wrapper invokes the resolved `clang` executable, losing C++ driver mode and automatic C++ library linkage. Clang explicitly derives driver mode from its invocation name. Preserve the absolute compiler path without dereferencing its final symlink. [LLVM driver implementation](https://clang.llvm.org/doxygen/ToolChain_8cpp_source.html)

3. **P2: Explicit Windows executable names silently bypass caching.** `kits/toolchain-cpp/templates/scripts/cc-cache.py:215` accepts `clang.exe` but creates `clang.exe.cmd`. Reproduce in PowerShell with LLVM and a cache installed: run `python scripts/cc-cache.py --shell powershell clang.exe`, evaluate its output, then invoke `clang.exe -c example.c`. PowerShell resolves the real `clang.exe`, not `clang.exe.cmd`; setup reports success but compilation never reaches the cache. The accepted compiler-name contract must either support explicit extensions or reject them clearly.
