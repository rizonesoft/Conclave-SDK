## Self-review

- Does it make sense: `endTree` is one loop over `TreeOps` (table, kill, running, clock): each round walks the table from every known process, so a descendant started between a look and a kill is found by the next look; it returns the processes still running at the deadline. Helpers run through `quiet` with a 3 s timeout (killed with SIGKILL), and `endTree` bounds each table read and kill as well, so a stalled helper still reaches the kill. `run` settles a stop with `survivors` and an error naming them; `parseTestRun` and `forgeOutcome` keep it as a cancel with a `note`.
- Is it logical: `ReviewerTester.test` returns its outcome at once but releases the one-test guard only when the cleanup (which waits for survivors before `withCandidate` deletes the pin) settles; the wait is bounded by the longest a run may last.
- Did it break anything: `killTree` now returns the survivors (`number[]`); its callers are `run` only. Unit 90 OK (2 skipped), run tests 13 of 13 in WSL, integration 40 passing, lint clean.
- Mutations: a single look fails the late-descendant test (and the deadline test); no helper bound makes the stalled-look test time out; unreported survivors fail the run test; deleting the pin without waiting for survivors fails the integration test.
- Known limit: on Windows a dead parent's id can be reused by an unrelated process within the five-second loop, which would then be treated as part of the tree; the window is the loop's length.

## Response to round 1

All five hold.

1. POSIX reparenting: where processes can be frozen, the whole tree is frozen before anything dies. The root is stopped, each look stops every new process it finds, and looks repeat until one finds nothing new; only then does the kill loop start. A child born just before its parent's stop is therefore found while its parent still holds it. Regression with a fake POSIX table (a killed parent's children go to init): the child born on its parent's stop is ended, and the tree is killed in one round with all three; without the freeze it is lost.
2. Unreadable tables: a look that cannot be read (a failed or stalled helper, or empty output) is `undefined`, never an empty table. `endTree` returns `{ survivors, verified }`, and the end is confirmed only by a look that was read and shows nothing running. `run` reports an unverified end in its error with `unverified: true`; both outcome parsers keep it as a cancel with a note. Regression: a stalled table with an unseen child reports `verified: false`; reading it as empty fails that.
3. Windows batches: one `taskkill /T /F` per round with at most 500 ids (`/T` restored, so taskkill also walks each tree), given 2.5 s, under the 3 s bound, so it has ended before the next round.
4. Guard after a deadline: survivors hold the one-test guard and the temporary pin for as long as they run, with no deadline, and a refused test names them (`A cancelled test's process 4242 still runs`). Regression: still refused after 1.2 s; a 1 s deadline fails it.
5. The record overclaimed: the fake table kept dead parents' ids, which hid finding 1, and the stalled case had no descendant, which hid finding 2. The fakes now model both, and the platform evidence is the real-process tests in `run.test.ts` (Windows and WSL).
