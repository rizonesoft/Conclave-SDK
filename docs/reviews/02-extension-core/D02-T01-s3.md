The pin's rules stay the dispatcher's. Six malformed replies are tested.
2. A candidate pin path is resolved against the folder once (`resolve`, injected) and that absolute path goes to both `--pin` and the layout read; the test failed on `346f80f`.
3. `onDidCheck` now carries only the folder's own pin and only its newest check; a candidate gets its verdict from the promise it asked for, so a candidate result is never published as the workspace's state and a late older check is not published over a newer one.
4. Scheduling is a pure `FolderQueue` (`src/core/folderQueue.ts`): one dispatcher process per folder at a time, an identical waiting or running request shares its answer, folders do not wait for each other, and a failed request does not block the next; unit-tested with hand-finished tasks.

## Response to round 2

Both hold; the round 1 response's "only the newest check is published" was not true while a running check could be shared.

1. The queue's semantics changed at the owning layer: an identical request shares a run only while that run is still waiting; once it has started, an identical request queues one fresh run behind it (further identical requests join that one). An answer therefore never predates its request: a pin saved while a check runs is read by the next check. `DispatcherClient` hooks each new run once with its own generation and publishes it only if no newer run was queued after it. Unit test: an identical request after the run started gets a fresh run, and both runs still never overlap. Host-level regression in `states.test.ts`, with a runner the test holds open (`DispatcherClient` now takes an optional runner): the first check runs on the valid pin, the pin is saved refused, the next check reads it, a check asked while another is running gets its own run, and the last published state is `refused` with no superseded `ready` after it.
2. This response records that verification.
