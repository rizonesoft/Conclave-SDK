# Review: D02 T01 §12 Extractor limits at tarfile's own parse

- Candidate: `f31fe2309b408ef9bb2c269ca1748007852207a0` (one commit; the leftover of `D02 T01 §7` round 3).
- Section: `todo/02-extension-core/TODO-01-extension-core.md` §12.

## Self-review

- Does it make sense: the limits now live where `tarfile` parses, so they see exactly the headers extraction sees. `Bounded._proc_member` runs for every header, including each link of a PAX or GNU chain (`_proc_pax` and `_proc_gnulong` call `fromtarfile` for the next header), and refuses on the header's own size before `_proc_pax` or `_proc_gnulong` reads the payload. `Capped` checks the stream position on every read and seek, since `tarfile` skips member data by seeking.
- Is it logical: overriding a private method is the only place the check can sit, as `TarInfo` has no public hook; `_proc_member` has been the dispatch since Python 3.2 and is present in 3.11 to 3.14. If a future Python renamed it, the override would simply not run and the size and member caps would remain, so the failure is open on memory, never on paths: path checks are separate.
- Did it break anything: the SDK's own `git archive` (492 files, with its PAX global header) extracts on Windows (3.14.4) and in WSL (3.12.3). Unit 70 OK (2 skipped), integration 19 passing, lint clean.
- Found while testing: on the `§7` extractor a 2000-header chain crashed with a `RecursionError` traceback (no JSON reply), and a sparse member was accepted; both are now refused with a reason.
- Mutation: with the stream cap disabled, the flood case (280 members with headers under 1 MB each) is accepted and the test fails.
