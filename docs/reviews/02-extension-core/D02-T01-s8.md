## Response to round 2

The finding holds: sending `SIGKILL` (or `TerminateProcess`) only starts a process's end, so `killTree` could return while one still ran. It now waits, at most 5 s, until every process it found has ended: on Linux by `/proc/<pid>/stat` (a zombie counts as ended), elsewhere by signal 0 (Windows reports a terminated process as gone). On Windows the tree is now read from the process table first (`Win32_Process` parent ids), so the wait knows every pid that `taskkill /T` ends; taskkill's own report is localized and cannot be read back.

The record advisory is right: the chain test observed after a `ps` spawn. Both cancellation tests now check every pid synchronously at the instant the run settles, with no grace: the 25-deep chain, and a new test repeating the reviewer's probe 20 times. Without the wait, the 20-run test fails in WSL (`run 3: process ... still running when the run settled`); on Windows `taskkill /F` had in practice already ended the processes, so the Windows run passes either way.
