Thousands of distinct prefixes remain within the archive, stream and member limits while consuming gigabytes, potentially killing the extractor before its JSON refusal. Use a component trie or another representation whose storage grows linearly with input length.

## Response to round 3

The finding holds, and it is a defect round 2's own fix brought in: the file-versus-folder check keeps every ancestor of every name as a separate string, so memory grows with the square of a path's depth. Round 3 is the last the loop allows, so the fix is filed as `D02 T01 §15`, "Extractor folder tracking linear in path length", Phase 1, run next: a component trie with integer node ids, each name walked once, and at most 64 components per name (the deepest path in the local repositories is 14). Until it ships the exposure is memory use on a hostile archive from a repository the operator chose; no file leaves the extraction folder and nothing from the archive runs. Verdict: stopped-at-3, leftover owned by `D02 T01 §15`.

Gates at `89784c7`: `node --test out/test/unit/extractSdk.test.js` passes on Windows and in WSL; the global path case is refused at its second member (on the end of `§12` the member limit refused it first); the SDK's own `git archive` (498 files) extracts.
