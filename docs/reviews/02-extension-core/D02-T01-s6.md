## Response to round 1

All four hold.

1. Reload during a save: load, save and the watcher's disk check now run one at a time on a per-session queue, so a reload asked during a save waits for it; and a save compares against the hash it captured when it started, not the session's current one. Either alone closes the reproduction. Regression: a reload started inside a paused save (and given 300 ms to finish) leaves the save `stale` with the other program's text kept; it fails only when both the queue and the captured baseline are removed.
2. A watcher read straddling a save: the disk check (`checkDisk`, what the watcher runs) is on the same queue, so it can no longer read before a save and compare after it. Regression with a `read` hook that holds the check's read while a save is asked: the saved pin is not marked stale; it fails without the queue.
3. Cleanup failure: the temporary file's removal now runs after the result is formed, and a removal that fails is appended to the result's message (the result's kind is kept); `save()` no longer rejects. Regression with a `remove` hook failing `EACCES` on a stale save.
4. The self-review's claim was wrong as finding 2 showed; the queue is what makes it true now.
