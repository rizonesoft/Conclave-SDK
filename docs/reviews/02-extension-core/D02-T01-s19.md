## Self-review

- Does it make sense: `FolderWork<T>` in `extensions/vscode/src/host/folderWork.ts` owns per-folder serialization, the cache, the lifetime captured when `read(folder)` is asked, the generation bumped by `invalidate`, and the rerun cap (five, then `unsettled`). Both services now hand it a computation and an `unanswered` answer; neither keeps its own queue.
- Is it logical: the computation receives `alive()` and both services call it before every `runForge`, so a forget during the first dry run (or `check`) starts no further forge process. A request asked before a forget answers `left` even when it runs after a later read has started the next lifetime.
- Did it break anything: every earlier kitState and kitHealth integration test passes unchanged (19 passing with repoInit); `npm test` 108 pass, 2 skipped; build and lint clean.
- Mutations: removing the per-process `alive()` checks fails the forget-while-held regressions in both suites; capturing the lifetime when the computation runs instead of when it is asked fails the asked-before-forget regression.
