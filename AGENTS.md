# AGENTS.md

Shared instructions for agents working in `Conclave-SDK`. Each agent loads this file alongside its own isolated entrypoint (`GEMINI.md`, `CLAUDE.md`, or `CODEX.md`).

## Purpose

`Conclave-SDK` holds the overlay kits (`kits/base`, `kits/todo`, `kits/reviewer`, `kits/automations`, `kits/launchers`, `kits/unattended`, `kits/lsp`, `kits/toolchain-cpp`, `kits/toolchain-web`, `kits/laravel`, `kits/wordpress`) that carry every agent skill, rule, subagent, script and template, plus prompts and the stdlib-only CLI `forge.py`, used to bootstrap projects. The SDK is a template: a project takes a copy once and owns it, and nothing links it back to the SDK. `forge.py` notes what it installed in the project's `.conclave/kits.json` (the SDK commit, each file's kit and a digest of its bytes as installed), a record with no path to the SDK that the project may delete.

## Operating directive

How to work without waiting to be told. When to ask the operator is listed under Safety, and only there.

- A task assigned is a task authorised: do it, then report what was done, with the evidence.
- Never end a turn with a question or an offer when the next step is known and unblocked: take the step.
- Finish the follow-ups this session can do safely (a config value, a setup step, a check to run again) and report them done, never as a list left for the operator.
- Ask the operator only for what Safety lists: once, with the options and the one you recommend, and keep working on everything the answer does not change.
- Fix forward: a risk found later is filed as ordinary work that blocks nothing, and a red check is fixed at its cause, never skipped or bypassed.
- Build the simplest design that meets the request in full, and add a check, gate or prerequisite only for a failure that has happened or one that would lose data, spend money or expose something.
- An unattended run never asks the operator: it takes the industry-standard option, records the decision and what reversing it would cost in the run file and files an owner item; it halts only through the run's own pause mechanism, and pauses instead of proceeding only for data loss, a credential, shared infrastructure or a calculation that looks wrong.

## Safety

- Local reversible work in the repository needs no confirmation, and neither does work outside it that the task authorised and that can be undone (a config value, a setup step, a deploy the task asked for).
- Ask the operator once before anything that destroys or exposes something, or that needs business context the repository lacks: dropping or overwriting data, a force-push, deleting outside the repository, creating, rotating or exposing a credential, sending mail or a message to a person, a SQL write or a production change with real blast radius.
- When a command needs sudo, give the operator the exact command to run with `! sudo ...`. Never store the sudo password.
- Never print, log, or commit a secret value.

## Git

A project with a branch workflow replaces the first rule with its own; the others hold everywhere.

- Develop on the main branch: commit there, with no feature branch, unless the operator asks for a branch in that task.
- Before staging, read `git status --short` and enough of the diff to understand every dirty file: another session or a person may be editing.
- Commit a safe side change (small, not secret, not generated, not in conflict) with the next coherent commit; stop and say why before touching one that conflicts, holds a secret or looks unsafe or generated.
- Never discard changes with `git reset`, `checkout`, `restore` or `clean` unless asked for that exact cleanup.
- After a commit, confirm it landed with `git log --oneline -1` and `git status --short`, and never filter hook output in a way that hides an error.
- When work is finished, remove the worktrees you or a subagent created, delete branches that are merged or whose content is verifiably on main, and prune dead worktree records.
- Never delete an unmerged branch whose content is not verifiably on main without asking.

## Autonomy and ambition

The owner's standing directive (2026-11-11), binding on every agent and every run in this repository, attended or not.

- **Decide and act.** A task assigned is a task authorised: do it, then report. Never stop to ask a question that the repository, its governing documents or sound engineering judgment already answers.
- **Ask only what cannot be decided here.** Ask before something that cannot be put back (dropping data, creating or exposing a credential, a force-push, deleting outside the repository) or that needs business context the repository lacks. Every other choice is made, recorded with what reversing it would cost, and built.
- **Heal what breaks.** A red gate, a failed tool, a stalled run or a wrong plan is work, not a stop: find the cause and fix it at its owning layer, with a test that would have caught it.
- **Improve the means as well as the product.** The repo, its runners, tools, kits and methods are changed whenever they slow the work or let a defect through, and the lesson is written where the next run reads it.
- **Be the best of its kind.** Measure each kit against the strongest alternative from any vendor, however large, and close what falls short. The completion review's comparison with that alternative is the measure, and "good enough" is not a verdict.
- **A person is needed only for what no tool can do.** A row waits on `operator`, `attended` or `owner-decision` only for a business decision the repository cannot make or a physical act no program can perform. An approval the owner's own tooling can grant through the vendor's own interface (Codex's hook trust through its app-server), a long-lived token in the vault, a config value or a one-time setup step is built into the tooling and done in the run, never filed for the operator. Found 2026-11-11: a live Codex proof was parked for a hook approval that Codex's own `config/value/write` grants.
- **Nothing is out of reach by default.** "Impossible" is a claim to test: break the problem down and build the smallest step that proves or disproves it before accepting a limit, then state any limit that remains with its evidence.
- **Finish.** Done means the work runs end to end, the checks pass, the documentation matches the code and nothing is left as a placeholder.

## Architecture and Working Rules

- **Zero external dependencies:** All Python scripts (`forge.py` and every script in the kits) use the Python 3 standard library only.
- **No machine or owner values in tracked files:** A folder on one machine, an owner's address, a vault item, a client's name or a project's location is never written into a kit, a script, a test or a document. It is a key in `.conclave/local.toml`, which git ignores, with its default and meaning in `.conclave/local.example.toml` (the base kit's file). A test uses neutral values (`example.com`, `C:\work`), and one that needs a neighbouring checkout finds it beside this one.
- **Atomic writes:** Every file write in tooling uses a temporary file in the destination directory followed by `os.replace`.
- **Strict agent isolation:** Each kit keeps Antigravity skills in `templates/.agents/`, Claude Code skills in `templates/.claude/` and OpenAI Codex skills in `templates/.codex/`, installed as the same folders in target repos. The kits are the only source, and within a kit the Claude file is the source of each skill: its Antigravity and Codex copies are generated from it plus the differences declared in the kit's `skill-patches/<agents|codex>/<skill path>.json`, so edit the Claude file or a patch, then run `python forge.py skill-copies` (a test fails while a committed copy differs from the generator's output; only Codex's `agents/openai.yaml` is kept by hand). The SDK's own `.agents/`, `.claude/`, `.codex/` and `scripts/` are an installed copy of the `base`, `todo`, `reviewer` and `automations` kits, as are `.conclave/reviewers.toml`, `.conclave/automations/`, `.conclave/local.example.toml` and the kits' files under `docs/`, because the SDK plans, reviews and schedules its own work with them: change a kit file in the kit, then refresh the copy with `python forge.py self-sync` (a test fails until the two match). The `launchers`, `unattended`, `lsp`, `toolchain-cpp`, `toolchain-web`, `laravel` and `wordpress` kits are not installed in the SDK itself. `scripts/start-run.ps1` (the launcher of the SDK's own unattended run) is the SDK's own file, in no kit. Default provisioning mode is `isolated` so every target repository is 100% self-contained.
- **Prose and table formatting:** Write one line per paragraph and list item in Markdown. Never use em dashes or en dashes anywhere: prose, code, comments, commit messages and generated files. Keep every Markdown table row at or under 120 characters so table rows never wrap in raw `.md` view, and keep TODO `Deliverable` cells and `## N. <Title>` headings to a short noun phrase of at most 88 characters.
- **TODO contract:** All skills and templates enforce small, single-responsibility sections, short `Deliverable` and section titles (`<= 88` chars), granular five-part micro-steps (`Done when:` and backticked path/symbol per item, `Cheaper substitute:` on UI/write items), logical step commits within sections, and a 100% complete development plan with zero silent drops or unowned SPEC controls.
- **Review:** The SDK reviews its own TODO sections three-pass, under `.conclave/reviewers.toml` (the reviewer kit's template pin): one plan review, one round, one completion review, then reconciliations after gaps, up to the pin's `pass_cap`. The SDK's own pin runs a repair-diff trial (owner, 2026-11-20, D00 T01 §10): a reconciliation, at medium effort, checks that the named gaps are closed and attacks only the newest repair's own diff (`repair-adversarial`, `repair-integration`), so edge cases in the rest of the section are hunted once, in the round; there is no `no_progress_cap`, and each trial section gets a shadow audit in the old full shape after its stamp. Tests follow the cadence below. A section keeps the pin committed at its plan review's candidate, so a pin change is committed before the next section starts.
- **Imported material:** `global/` (the owner's machine-level rules, hooks and skills for Claude Code and Codex) and `plugins/` (account-bound MCP plugins) were imported byte for byte from two retired repositories. `forge.py` never installs either into a project, and only their two `README.md` files are held to the writing rules above; change an imported file only on purpose, never to satisfy a formatter. The findings files under `docs/reviews/` hold reviewers' replies byte for byte under a digest and are exempt too.
- **Output discipline:** Bound command output, and redirect full logs to scratch.
- **Test cadence (owner, 2026-11-13):** CI does the heavy lifting, so the local loop stays fast. `python forge.py check-all` is the one command that runs every suite the repository holds (its `SUITES` table in `forge.py` is the one list of them; `--full` adds the gated stamp and adoption tests, `--only <name>` and `--skip <name>` choose suites), and `.github/workflows/tests.yml` runs it on every push to main: the quick suite (`check-all --only tests`) on Windows and the full suite (`check-all --full --only tests`) on Linux, each in three parallel shards (`--shard 1/3`, `2/3`, `3/3`: the same tests, split by file and balanced by the measured seconds in `tests/shard-seconds.json`, which a new slow file is added to), and every other suite (`check-all --full --skip tests --skip kit-unattended`: each kit's own, the SDK's installed copy and the agent checks) on Linux with tmux; the unattended kit's suite runs once per OS, from its installed copy in `tests/test_unattended_installed*.py`. Locally: while building or fixing, run only the tests that cover the change (the affected test file or a `-k` selection, plus a mutation check for a review fix); per review pass, again only the tests that cover that pass's fixes (owner, 2026-11-19: a full kit suite before every pass cost 15 to 25 minutes each); the touched kit's own suite once, on the candidate the stamp will name (Windows; CI's `kits-linux` job runs its tmux half), and `tests.test_forge` for the kit's installed copy when the kit's tests changed; a commit that changes only records or documentation runs only the Markdown format check (`python -m unittest tests.test_forge -k markdown_table`, under a second), which caught nothing locally on 2026-11-13 because it was skipped and turned main red. A section's suite evidence is the green CI run of the commit it stamps, cited in the stamp's `--check` (a run a newer push cancelled is rerun on that commit with `ci_status.py --rerun`; when that commit's run is red for a failure fixed outside the section after its review chain closed, the stamp cites the red run and the green run of a commit that holds the reviewed fix and the section's own reviewed files and TODO section unchanged apart from it); run `python forge.py check-all --full` (or one suite of it with `--only`) locally only when CI cannot answer (`ci_status.py` exit 3) or to reproduce a red. Commit locally through the plan review, the round and its fixes, and push once, when the completion review starts, so CI runs beside it and `main` only gets work that passed the round (owner, 2026-11-19); the stamp waits for that push's run to be green. After every push and at every section boundary `python scripts/ci_status.py --since-last` reads CI (it only reports, and never holds a commit or a push), and a red main comes before any new row: read the failed job's log, fix it at its owning layer with a regression test, or rerun an infrastructure failure (once, and once more after an outage has cleared, each red run kept).
